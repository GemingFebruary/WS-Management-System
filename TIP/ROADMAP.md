# 项目调整方向与修改路线（基于开题报告）

> 依据：2026-11 开题报告《基于微信小程序的高校校园勤工助学服务平台的设计与实现》；2026-11-15 开题答辩已通过（同意开题）。
> 创建：2026-11-19

---

## 一、开题报告核心要求

1. **定位**：后端（云函数 + 云数据库）承担数据存储与接口支撑，**不作为研究重点**；研究聚焦**小程序端**的页面组织、交互逻辑、匹配结果呈现方式与工程质量。
2. **模块**：7 个一级模块、21 个二级子模块，形成"一级模块—二级子模块—页面"三级映射。
3. **匹配模型**：**可配置的多维加权人岗匹配**——技能标签匹配度、可工作时间重合度、岗位类型偏好、年级与课程冲突；权重由管理人员在系统设置中配置；输出匹配度评分、权重分解、匹配依据。
4. **数据可视化**：**ECharts（ec-canvas）** 展示岗位供需比、申请通过率、人均工时、酬金分布等。
5. **前端工程**：rpx + 弹性布局、公共组件封装（弹窗/提示/空状态/表单/分页）、表单校验、权限控制、请求统一封装（缓存 + 去重）、安全处理。
6. **创新点**：可配置匹配模型 + 匹配度可视化；数据统计可视化。
7. **延伸**：贫困补助模块（优先推荐贫困生）。

---

## 二、当前实现与开题要求的差距

| 维度 | 当前实现 | 开题要求 | 差距 |
|------|---------|---------|------|
| 匹配模型 | 固定权重（专业 30% / 年级 20% / 成绩 25% / 时间 25%），后端计算 | 可配置多维加权（技能标签 / 时间重合 / 岗位类型 / 年级课程冲突），权重可配置 | 🔴 大 |
| 匹配呈现 | 分数 / 列表 | 分数 + 权重分解 + 匹配依据可视化 | 🔴 大 |
| 数据可视化 | 列表 + JSON/CSV 导出 | ECharts 图表 | 🔴 大 |
| 模块覆盖 | 16 页（11 顶层 + 5 admin） | 7 模块 21 子模块 | 🟡 中 |
| 学生画像 | users 基础字段 | 技能标签、可工作时间、岗位偏好、贫困标识 | 🟡 中 |
| 公共组件 | 无自定义组件（usingComponents 全空） | 封装弹窗/提示/空状态/表单/分页 | 🟡 中 |
| 请求层 | util.callXxx 基本封装 | 统一封装 + 缓存 + 去重 | 🟢 小 |
| 双端范围 | 小程序 + QGWEB + QGPY | 聚焦小程序端 | 🟡 定位需收敛 |

## 三、修改路线（五阶段）

### 阶段 1：匹配模型重构（最高优先级）
- 扩展用户模型：技能标签、可工作时间段、岗位类型偏好、年级/课程、贫困标识。
- 扩展岗位模型：技能标签、岗位类型、工作时间要求。
- 匹配算法改为**可配置多维加权**（4 维度），权重存储于系统设置集合，支持管理员调整。
- 输出：匹配度（0–100）、权重分解、匹配依据。
- 涉及：云函数（jobs.recommend / 新增 match）、数据库字段、管理端权重配置页。

### 阶段 2：匹配度可视化
- 岗位详情/推荐列表展示匹配度进度条、维度分解、匹配依据。
- 新增学生端"智能匹配"页面。

### 阶段 3：数据统计可视化
- 引入 ec-canvas / ECharts。
- 管理端数据统计页：岗位供需比、申请通过率、人均工时、酬金分布。
- 保留导出能力。

### 阶段 4：模块补全与组件化
- 对照 21 个二级子模块补全页面（系统设置、操作日志、数据备份、岗位分类字典、技能标签维护、贫困补助等）。
- 封装公共组件：Modal / Toast / EmptyState / Form / Pagination。
- 请求层统一封装 + 缓存 + 去重；表单校验、权限、安全加固。

### 阶段 5：测试与论文
- 功能 / 兼容性 / 性能测试用例（`文档/测试用例.xlsx` 已有）。
- 多真机验证。
- 撰写论文对应章节。

## 四、范围与定位建议

- 论文以**小程序端**为主线；QGWEB / QGPY 作为支撑或对比，简要提及，避免喧宾夺主。
- 后端云函数仅作支撑，不展开为研究重点。

---

## 五、风险与依赖

- ECharts 小程序包体积（ec-canvas）较大，需注意**分包**，避免主包超 2MB。
- 云数据库字段扩展需数据迁移与兼容处理。
- 匹配模型变更影响现有推荐/申请流程，需回归测试。
- 真机调试受开发者工具登录态与包体积影响，需保持登录有效。
